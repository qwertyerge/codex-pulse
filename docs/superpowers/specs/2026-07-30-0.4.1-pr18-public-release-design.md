# Codex Pulse 0.4.1 PR #18 Public Release Design

**Status:** Approved design
**Date:** 2026-07-30
**Target PR:** [#18](https://github.com/qwertyerge/codex-pulse/pull/18)
**Target version:** `0.4.1`

## Context

Codex Pulse `0.4.0` is the private updater bootstrap installed on the
maintainer's macOS ARM64 machine. Its GitHub Release remains a Draft, while its
annotated Git tag remains visible in the public repository. The Draft assets
and `latest.json` are not public and `0.4.0` must never be published.

PR #18 contains the next public product changes:

- official weekly quota observations from Codex App Server;
- Windows refresh scheduling and transcript-settle hardening;
- hidden Windows Git child-process consoles;
- Windows maximize behavior and width constraints; and
- dark footer corrections.

The PR was opened from `0.3.2` before the signed updater and `0.4.0` bootstrap
landed on `main`. Its original remote head was
`47d4f00e1a2a5f73101efb732f1f110cc612157b`, while the approved integration
base is `origin/main@74dade8caffbc7413f95ba6619df9c5015e57634`.

The release must make `0.4.1` the first public updater-capable version. Public
`0.3.2` installations do not contain the updater and therefore require one
manual installation. The maintainer's private `0.4.0` installation is the sole
bootstrap used to prove the first real automatic update.

## Goals

1. Reuse PR #18 rather than opening a separate release PR.
2. Rebase PR #18 onto the exact signed-updater mainline.
3. Resolve every current actionable PR review thread before release.
4. Change exactly the four owned version sources to `0.4.1`.
5. Produce and authenticate a two-platform `0.4.1` Draft release.
6. Require a separate human approval immediately before publication.
7. Publish `0.4.1` as a non-prerelease and prove a real macOS
   `0.4.0` to `0.4.1` automatic update.

## Non-Goals

- Publishing the `0.4.0` GitHub Release.
- Deleting the public `0.4.0` annotated tag.
- Deleting the private `0.4.0` Draft or its assets.
- Rotating, reading, printing, or otherwise mutating updater signing secrets.
- Creating a replacement PR for PR #18.
- Claiming a Windows interactive installation or automatic-update result.
- Making `0.3.2` automatically update; it has no updater runtime.
- Removing Windows support from the public release.

## Source and Git Integration

The branch remains `codex/integrate-four-fixes`. It is rebased onto the exact
approved `origin/main` instead of merging `main` into the feature branch.

The original PR head is a two-parent merge commit. A normal linear rebase does
not replay that merge commit, so the integration must explicitly preserve the
merge-only `drop(state)` before ownership of the Tauri app handle moves into
`start_refresh`. The allowed reconciliation is a dedicated one-line
integration commit, followed by a tree-parity check against the synthetic
`main + original PR head` merge tree.

The local design-preparation rebase produced integration commit
`4e3a8031d885b90d1e893b51014c9ab8d430d24b`. This is local evidence only. It
does not update the remote PR and does not authorize implementation.

When implementation is approved, the same PR branch is updated with an exact
lease:

```text
--force-with-lease=codex/integrate-four-fixes:47d4f00e1a2a5f73101efb732f1f110cc612157b
```

The push must fail rather than overwrite any remote update that moved the old
head. No direct push to `main` is permitted.

## Review Hardening

All three current unresolved review threads are release blockers:

1. A Windows maximize-width subclass failure must degrade gracefully and must
   not abort application startup.
2. The Windows Git child-process test must exercise the real command
   configuration seam and prove `CREATE_NO_WINDOW` is applied before spawn,
   rather than only asserting a constant.
3. The refresh design and plan must describe window maximization as outside
   the refresh/console cohort, rather than globally out of scope, so they do
   not contradict the Windows `0.3.0` acceptance scope.

One additional reviewed documentation hardening remains in scope: the same
refresh records must distinguish earliest-deadline behavior for coalesced
recent events from latest-deadline behavior for the hook transcript-settle
quiet period.

Each code behavior change begins with a focused failing test. The
implementation is the smallest change that makes that test pass. Documentation
changes receive exact-text and consistency checks. Review threads are resolved
only after the current exact head contains the fix and the relevant
verification is green.

## Version Ownership

The following four values are the complete version-edit boundary:

1. `package.json` root `version`;
2. `src-tauri/Cargo.toml` root package `version`;
3. the `codex-pulse` package entry in `src-tauri/Cargo.lock`; and
4. `src-tauri/tauri.conf.json` root `version`.

`src/__tests__/updaterConfiguration.spec.ts` remains the ownership-aware
contract. The test is first changed to require all four values to equal
`0.4.1`, observed failing against the rebased `0.4.0` tree, and then made green
by editing only the four owned values.

Fixture strings that merely model arbitrary updater versions are not bulk
rewritten. A literal changes only when it represents the repository release
version rather than test data.

## PR #18 Release-Candidate Gate

Before PR #18 can be considered a `0.4.1` release candidate:

- the rebase base is the exact approved `origin/main`;
- the aggregate PR behavior is preserved across the linear rebase;
- the three review blockers are fixed and their threads are resolved;
- the additional deadline-semantics documentation hardening is present;
- all four owned version sources equal `0.4.1`;
- the PR body describes the user-visible `0.4.1` changes and current
  verification;
- focused red/green evidence is recorded;
- the full frontend and Rust gates pass;
- the exact remote PR head matches the tested local head;
- GitHub exact-head CI passes on frontend, Rust, and Windows; and
- an independent review has no unresolved Critical or Important finding.

The existing CI run for original head `47d4f00...` is historical evidence only
and cannot satisfy this gate.

After these conditions are met, the maintainer receives an evidence summary
and separately approves the squash merge. A green PR is not merge permission.

## Exact-Main and Tag Gate

After the approved squash merge:

1. fetch `origin/main` and identify the exact squash-merge SHA;
2. wait for the CI run whose head is exactly that SHA;
3. require every release-relevant job to succeed;
4. re-read all four version sources from that exact SHA;
5. confirm the source tree is clean and no newer mainline replaced it; and
6. create annotated tag `0.4.1` at that exact SHA.

Only the tag is pushed. The release workflow's source guard must validate that
tag, version, and mainline provenance before platform builds proceed.

## Draft Release Gate

The release workflow must create `0.4.1` as:

- `draft=true`;
- `prerelease=false`;
- `published_at=null`; and
- targeted at the exact tagged mainline SHA.

The authenticated Draft must contain:

- macOS ARM64 DMG;
- macOS ARM64 updater `.app.tar.gz`;
- adjacent macOS updater `.sig`;
- Windows x64 NSIS setup executable;
- adjacent Windows updater `.sig`; and
- one `latest.json`.

The Draft gate independently verifies:

- GitHub asset sizes and SHA-256 digests;
- the version and required platform keys in `latest.json`;
- every manifest URL against the actual Draft asset ID;
- signature fields against the adjacent signature assets;
- both updater signatures using the committed public key with legacy
  verification disabled;
- negative cross-signature rejection;
- macOS archive and DMG structure, arm64 architecture, version, bundle ID,
  executable parity, and strict bundle signature;
- Windows installer structure and signed updater payload;
- release workflow completion and final manifest-verifier success;
- public `/releases/latest` still points to the previously published release
  while `0.4.1` is Draft; and
- signing-secret metadata remains unchanged.

No Draft result authorizes publication.

## Publication Gate

After all Draft checks pass, the maintainer receives the exact tag, commit,
workflow run, asset inventory, hashes, signature evidence, public-boundary
checks, secret metadata timestamps, and remaining acceptance scope.

The GitHub publish action requires a fresh explicit approval at that moment.
With approval, `0.4.1` is published as a normal non-prerelease. The resulting
public state must satisfy:

- `draft=false`;
- `prerelease=false`;
- non-null `published_at`;
- `/releases/latest` resolves to `0.4.1`; and
- public `latest.json` and updater payload URLs return the exact verified
  assets.

The published release notes must state that `0.4.1` is the first public
updater-capable version and that existing `0.3.2` users need one manual
installation before future automatic updates.

## macOS Automatic-Update Acceptance

Before exercising the production updater, preserve the installed private
`0.4.0` bundle as a timestamped, recoverable backup and verify that backup's
version, executable hash, and strict signature.

The live acceptance uses the installed `/Applications/Codex Pulse.app` and
Computer Use:

1. quit and relaunch private `0.4.0` to trigger its immediate production
   update check;
2. observe discovery of public `0.4.1`;
3. observe automatic download progress and the ready state;
4. activate the ready update;
5. observe the native confirmation dialog;
6. approve installation and allow the updater to relaunch the app; and
7. inspect the relaunched UI and installed bundle.

The final installed proof requires:

- version `0.4.1`;
- arm64 executable;
- strict bundle signature;
- expected CDHash;
- installed executable SHA-256 matching the authenticated updater archive;
- one process from `/Applications/Codex Pulse.app`;
- a new process ID after relaunch;
- no repeated ready or failed updater prompt for `0.4.1`;
- active task cards and current recent events;
- successful background reconciliation; and
- weekly quota rendering independent of updater state.

This is the only required interactive update path. Windows evidence is limited
to CI plus authenticated Draft asset, manifest, structure, and signature
checks, and must be labeled accordingly.

## Secrets and Security

The existing updater signing identity is reused unchanged. The task may inspect
secret names and `updatedAt` metadata but never secret values. It must not
rotate, delete, recreate, export, print, or persist the private key or password.

The independent offline recovery evidence remains unchanged. A successful
release does not justify touching signing material.

## Failure and Rollback

- Rebase or focused-test failure: do not push the PR branch.
- Lease mismatch: stop and inspect the new remote head; never force past it.
- PR CI or review failure: do not merge.
- Exact-main CI failure or drift: do not tag.
- Release workflow or Draft verification failure: keep `0.4.1` as a Draft and
  do not publish.
- Missing final publication approval: keep `0.4.1` as a Draft.
- Post-publication macOS updater failure: restore the local `0.4.0` backup,
  retain complete evidence, and report the public release honestly.

A post-publication functional failure does not authorize deleting or rewriting
the public `0.4.1` tag or release. The normal recovery is a separately approved
forward fix such as `0.4.2`. Security incidents require a separate takedown
decision.

## Automated Verification

The implementation plan must include, at minimum:

- focused red/green tests for the two code review blockers;
- exact-text checks for the cohort-scope and deadline-semantics documentation;
- the four-source `0.4.1` ownership contract;
- `pnpm test`;
- `pnpm build`;
- serial `cargo test --manifest-path src-tauri/Cargo.toml`;
- `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check`;
- `git diff --check`;
- exact-head GitHub CI and review;
- exact-main GitHub CI before tagging;
- release workflow and manifest-verifier evidence; and
- the manual macOS updater acceptance described above.

Focused, full-suite, CI, Draft, publication, and installed-app evidence are
distinct gates. Success at one gate must not be reported as success at another.

## Completion Criteria

This release task is complete only when all of the following are true:

- PR #18 was rebased, hardened, versioned as `0.4.1`, reviewed, and merged with
  explicit approval;
- exact-main CI passed;
- annotated tag `0.4.1` points to that exact mainline SHA;
- the two-platform Draft passed all artifact and signature gates;
- the maintainer explicitly approved publication;
- `0.4.1` is the public latest release;
- the private installed macOS `0.4.0` completed a real automatic update to
  installed `0.4.1`;
- monitoring and official quota behavior remained functional after relaunch;
- `0.4.0` remains an unpublished Draft with its public tag retained;
- signing secrets were not mutated; and
- Windows interactive acceptance is reported as not performed.
