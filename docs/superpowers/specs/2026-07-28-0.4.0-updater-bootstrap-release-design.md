# Codex Pulse 0.4.0 Updater Bootstrap Release Design

## Context

Codex Pulse `0.3.2` is the current published GitHub Release. Its release
contains one macOS ARM64 DMG and one Windows x64 NSIS installer, but no updater
manifest, updater archive, or updater signature. Those installed binaries
cannot discover or authenticate a later release.

PR #17 added signed automatic-update support and was squash-merged as
`1aaaaaedb50f3d5b8ec77abab28704d8c9e1a4cc`. The exact merge commit passed
GitHub Actions run `30353144486`, including Frontend, macOS Rust, Windows Rust,
the unsigned PR-build NSIS package, and Windows package verification.

The repository currently has GitHub Actions Secrets named
`TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Their
values are write-only and are not a backup. The maintainer reports that an
offline backup exists, but independent restore evidence has not yet been
provided.

## Goal

Prepare the first updater-capable version as `0.4.0` through a separate,
reviewable version pull request while preserving independent gates for:

1. updater feature integration;
2. version preparation;
3. signing-material recovery evidence;
4. tag and Draft artifact generation;
5. manual bootstrap installation;
6. publication; and
7. the first real production update from `0.4.0` to `0.4.1`.

This task ends with a green, open `0.4.0` version PR. It does not create a tag
or release.

## Non-Goals

- Merging the `0.4.0` version PR.
- Creating or pushing a `0.4.0` tag.
- Triggering, publishing, editing, or deleting a GitHub Release.
- Reading, printing, replacing, or rotating signing-secret values.
- Treating GitHub Secrets as offline recovery material.
- Installing or replacing the local Codex Pulse application.
- Claiming a real old-version-to-new-version automatic update.
- Changing the updater endpoint, public key, Windows install mode, update UI,
  schedule, privacy behavior, or release workflow.
- Rewriting historical `0.3.2` design, plan, fixture, README, or acceptance
  evidence before `0.4.0` is actually published.

## Chosen Release Train

### Feature Gate

The updater feature PR is integrated first and independently. Its squash merge
commit must pass all required checks on `main` before version work starts. A
failed main check stops the train; version preparation never branches from a
red mainline.

This gate is satisfied by merge commit
`1aaaaaedb50f3d5b8ec77abab28704d8c9e1a4cc` and GitHub Actions run
`30353144486`.

### Version Gate

Branch `codex/release-0.4.0` starts at the exact green feature merge. It
contains the design and implementation plan, one ownership-aware version
contract, the four synchronized version sources, and a durable bootstrap
readiness report.

The branch is pushed through a Ready PR targeting `main`. The PR must reach an
exact-SHA green state for Frontend, Rust, Rust (Windows), and CodeRabbit. It
then remains open while the maintainer supplies independent offline-backup
evidence.

No tag or Draft is created from an open version PR.

## Version Contract and File Boundary

The release version changes from `0.3.2` to `0.4.0` in exactly four version
sources:

| File | Owned value |
| --- | --- |
| `package.json` | root `version` |
| `src-tauri/Cargo.toml` | root `[package].version` |
| `src-tauri/Cargo.lock` | the `[[package]]` entry whose name is `codex-pulse` |
| `src-tauri/tauri.conf.json` | root `version` |

`src/__tests__/updaterConfiguration.spec.ts` becomes the executable contract
for those four owned values. The test first expects all four to equal `0.4.0`
and fails against the unchanged sources. The implementation then changes only
the owned values and makes the focused test pass.

The Cargo lockfile must not be changed with a global `0.3.2` replacement:
unrelated dependencies legitimately use that version. The test locates the
package block by `name = "codex-pulse"` before reading its version.

The version PR also adds:

- this design;
- `docs/superpowers/plans/2026-07-28-0.4.0-updater-bootstrap-release.md`; and
- `docs/superpowers/reports/0.4.0-updater-bootstrap-readiness.md`.

The following remain unchanged because they describe current or historical
facts:

- English and Chinese README statements that `0.3.2` is the current published
  installer and does not contain the updater;
- existing automatic-update designs and plans whose approved boundary kept
  version `0.3.2`;
- `0.3.2` fixture values in the local macOS signing-runbook tests; and
- prior acceptance reports.

## Bootstrap Readiness Record

The readiness report is the durable handoff for later release tasks. Every gate
uses one of these states:

- `verified`: backed by an exact commit, run, artifact, timestamp, or observed
  platform result;
- `pending-user-evidence`: the maintainer reports completion but has not yet
  supplied independently reviewable proof;
- `blocked`: a prerequisite failed or is missing; and
- `not-started`: no attempt has been made.

Automated success never implies manual installation, publication, or user
acceptance.

The initial report records:

- published `0.3.2` release state and its two non-updater assets;
- PR #17 merge SHA and exact-main CI run;
- `0.4.0` version-source and version-PR evidence as it is produced;
- signing-secret names and update timestamps only;
- offline backup as `pending-user-evidence`; and
- tag, Draft, artifact inspection, manual installation, publication, and
  cross-version update as `not-started`.

No key contents, passphrase, Keychain value, backup path, or sensitive medium
identifier is written to the repository or PR.

## Offline Backup Gate

Before any `0.4.0` tag is created, independent evidence must establish all of
the following without exposing secret values:

1. the encrypted updater private key exists on a medium independent of the
   developer machine and GitHub Secrets;
2. the passphrase is recoverable from separately protected storage;
3. a restored copy can sign a benign fixture; and
4. the resulting signature verifies against the public key committed in
   `src-tauri/tauri.conf.json`.

Merely listing GitHub secret names, checking the original local key, or copying
the encrypted file without exercising the passphrase does not satisfy this
gate.

The backup gate does not block opening the version PR, but it blocks merging
that PR for release execution and blocks tag creation until the maintainer
provides the agreed evidence.

## Two-Stage Bootstrap and Update Acceptance

The production endpoint is fixed at:

`https://github.com/qwertyerge/codex-pulse/releases/latest/download/latest.json`

Tauri's JavaScript `check()` API accepts request options but does not override
that endpoint at runtime. GitHub defines the latest release as a published,
non-Draft, non-prerelease release. Therefore, an exact `0.4.0` production
binary cannot discover a `0.4.1` Draft before `0.4.0` is published.

The rollout is consequently split into two honest stages.

### Stage 1: 0.4.0 Manual Bootstrap

A later, separately approved task:

1. merges the version PR and re-verifies the exact main SHA;
2. creates the strict annotated `0.4.0` tag;
3. waits for the serialized two-platform Draft workflow;
4. authenticates to the Draft and verifies the DMG, NSIS installer, updater
   artifacts/signatures, and two-platform `latest.json`;
5. manually installs the exact Draft assets on macOS ARM64 and Windows 11 x64;
6. verifies installed version, launch/restart, session monitoring, and updater
   failure isolation while the Draft remains unavailable at the public latest
   endpoint; and
7. obtains explicit publication approval.

Published `0.4.0` is described as the manually installed updater bootstrap,
not as proof that automatic updating already works end to end.

### Stage 2: First Production Automatic Update

A subsequent `0.4.1` release uses the same signing key and release workflow.
After `0.4.1` is published, installed `0.4.0` applications can discover it
through the real production endpoint. Acceptance then observes, on both
platforms:

- scheduled or retried update discovery;
- signed artifact download and verification;
- native install confirmation;
- installer handoff and restart;
- installed version `0.4.1`; and
- continued session-monitor operation.

The automatic-update rollout is not called fully accepted until this
post-publication `0.4.0` to `0.4.1` path passes.

Adding a maintainer-only endpoint override or replacing GitHub Releases with an
independent manifest service was rejected to avoid expanding runtime and
security scope solely for prepublication testing.

## Failure Handling

- If the feature merge's exact main CI fails, stop before creating or updating
  the version branch.
- If a remote branch moves or diverges, fetch and reassess; never force-push as
  a shortcut.
- If the focused version contract or full local suite fails, keep the version
  branch local until diagnosed.
- If version-PR CI or review fails, keep the PR open and require a new exact-SHA
  green run after correction.
- If backup evidence, Draft assets, manifest validation, signatures, or either
  manual platform installation fails, keep the release as a Draft.
- Do not delete published assets, rotate the signing key, or fall back to
  unsigned updater metadata as an incident response. Recovery uses a separately
  approved, signed roll-forward release.

## Verification

Version preparation runs:

```text
pnpm test -- src/__tests__/updaterConfiguration.spec.ts
pnpm test
pnpm build
cargo fmt --check --manifest-path src-tauri/Cargo.toml
cargo test --manifest-path src-tauri/Cargo.toml
git diff --check
```

It also inspects:

- the exact four owned version values;
- the Cargo lockfile diff for unrelated package-version changes;
- the complete branch diff against the green feature merge;
- repository status for secret material and unrelated files; and
- the version PR's exact head SHA and every required check.

## Completion Criteria

This task is complete only when:

- PR #17 is squash-merged and its exact main CI is green;
- `codex/release-0.4.0` is based on that exact green merge;
- the approved design and implementation plan are committed;
- all four version sources and the version contract equal `0.4.0`;
- the readiness report distinguishes verified, pending, blocked, and
  not-started gates;
- local verification passes;
- a Ready `0.4.0` PR is open with exact-SHA green CI and review status; and
- the PR remains unmerged with no tag, Draft, publication, or app replacement.
